# この報告の要旨

前回（10月4日）の報告で，実験C2.1（H-C2″）が3関数すべてで支持され，次の
優先度として「$N=100$まで伸ばして崩壊点を確定する」ことを挙げた。今週は
その着手として，まず $N=26$ で保留していた前提（$d_{model}=128$の崩壊が
warmupで直るかどうか）を確認し，次に $N=100$ への拡張そのものに取り組んだ。

1. **warmup予備実験（$N=26$）**：$d_{model}=128$の崩壊が warmup で直るか，
   統制 $h$ も含めて検証した。
2. **$N=100$段階A（データ量）**：統制 `func_pow_k100` がどのデータ量で天井に
   届くかを確認した。
3. **$N=100$・warmup**：段階Aで見つかった停滞が warmup で直るか確認した。
4. **$N=100$・学習率**：停滞が学習率過大によるものか確認した。
5. **$N=100$・容量**：$d_{model}$を増やせば停滞が直るか確認した。
6. 以上4軸がいずれも効かなかったことを受け，$N=100$への拡張を一旦停止する
   判断をした。

以下は結論の先出しである。用語と関数の定義は末尾の付録に記す。

## 何が分かったか

**① $d_{model}=128$の崩壊はwarmupで直るが，これは$j$項との相性に限られる。**
統制$h$は$d_{model}=128$でwarmupの有無に関わらず全く同じ値（2/3，同一鍵で
同一の正解率）であり，warmupが効いたのは$f_{2,2}$だけだった（0/3→2/3）。

**② 実装を確認すると，$N$が効くのは系列長ではなく値の埋め込みの語彙数だった。**
Transformerへの入力系列長は$N$によらず常に14トークン固定で，$N$が増えると
増えるのは各トークンが取りうる値の種類数（埋め込みテーブルの語彙数）である。

**③ $N=100$の統制は，データ量を4倍にしても変化しなかった。** 50,000→
100,000→200,000件で平均正解率は0.2496→0.1642→0.1620。200,000件の
検証正解率の履歴はエポック0〜29まで完全に平坦で，「まだ上昇中」ではなく
**最適化がそもそも始まっていない**形だった。

**④ warmupは離陸する鍵の顔ぶれを入れ替えただけだった。** 離陸数は
1/5→1/5で変わらず，warmup無しで離陸していた鍵が落ち，別の鍵が上がった。

**⑤ 学習率を下げても直らず，下げすぎるとむしろ悪化した。** 1e-3→3e-4は
ほぼ無変化。1e-4まで下げると唯一の離陸鍵まで床に落ちた。

**⑥ 容量（$d_{model}$）を増やしても直らず，むしろ収束が鈍った。** 残り4/5の
鍵は$d_{model}$を32→64→128に増やしても一度も床から動かなかった。warmup下で
唯一離陸する鍵も，$d_{model}=128$では1.0000ではなく0.5022止まりだった。

**⑦ $N=26$で効いた3軸（warmup・学習率・容量）はいずれも$N=100$統制の
停滞を動かせず，$N=100$への拡張を一旦停止する判断をした。**「$j$項の壁は
アーキテクチャ依存（CNN固有）」と「スケールの壁はアーキテクチャに依らず
別に存在する」という，2つの異なる壁を区別できたことを成果として整理する。

# 今回の結果

## warmup予備実験（$N=26$）：$d_{model}=128$の崩壊はwarmupで直るが，統制は無関係

$d_{model}=128$での崩壊は，post-LN構成でwarmupが無いためという推測のまま
$N=100$スケーリングの前提になっていた（未検証）。`src/baseline_ml/models.py`
に線形warmup（warmup後は減衰させず一定。実験7・11で踏んだ「予算とスケジュール
を同時に変える」問題を避けるため，減衰は入れない）を追加し，`train_pathC.py`
に`--warmup_epochs`を追加して検証した（`experiments/batch/run_warmup_probe.sh`）。

$f_{2,2}$だけで測ると「容量とwarmupなしの組み合わせがタスクに依らず不安定」
なのか「$j$項の難しさとの相性」なのかを区別できないため，統制$h$（`func_pow`）
も同じ格子に含めた（鍵3本，$N=26$・50,000件・30エポック，既存の構成感度実験と
同条件）。

| 関数 | $d_{model}$ | warmup無し | warmup 5エポック |
| :--- | ---: | :--- | :--- |
| $f_{2,2}$ | 32 | 2/3（0.84, 0.91, 0.36） | 2/3（0.84, 0.27, 0.93） |
| $f_{2,2}$ | 64 | 2/3（0.97, 0.26, 0.94） | 2/3（0.79, 0.26, 0.91） |
| $f_{2,2}$ | **128** | **0/3**（0.41, 0.48, 0.31） | **2/3**（0.97, 0.26, 0.88） |
| $h$（統制） | 32 | 3/3 | 3/3 |
| $h$ | 64 | 3/3 | 3/3 |
| $h$ | 128 | 2/3 | 2/3（同一鍵で完全に同じ値） |

: $N=26$・50,000件・30エポックでのwarmup有無の比較（鍵3本）

$d_{model}=128$での$f_{2,2}$の崩壊はwarmupで直る（0/3→2/3）が，統制$h$は
$d_{model}=128$でwarmupの有無に関わらず**全く同じ値**（2/3，同一鍵で同一の
正解率）であり，warmupは統制には何も変えていない。したがって「容量×warmup
なしの組み合わせがタスクに依らず不安定」という説明は否定され，問題は
**「大きい容量×warmupなし×$j$項という難しいタスク」の組み合わせに限られて
いた**。統制だけで検証していたら「warmupは効かない」と誤って結論するところ
だった。

## $N=100$段階A：データ量だけでは統制は天井に届かない

小川さんらの報告では$N=100$の統制は50,000件で最大0.2118（データ密度不足）
だったため，容量・warmupは$N=26$の既定（$d_{model}=32$・`cls`・2層・warmup
なし）に固定し，データ量だけを50,000/100,000/200,000で振った
（`experiments/batch/run_n100_datasize_probe.sh`，鍵5本）。

| データ量 | 検証最大（平均±sd） | 最大値 |
| :--- | :---: | :---: |
| 50,000 | 0.2496±0.1523 | 0.5102 |
| 100,000 | 0.1642±0.0569 | 0.2118 |
| 200,000 | 0.1620±0.0538 | 0.2037 |

: $N=100$・統制 `func_pow_k100`・データ量ごとの検証正解率（鍵5本）

データを4倍にしても変化がなかった。200,000件の`history.val_accuracy`を
確認すると，エポック0〜29まで完全に平坦（例：鍵20260928は全エポックで
0.104で一定）だった。「まだ上昇中で打ち切りが早すぎた」のではなく，
**最適化がそもそも始まっていない**形である。これは$N=26$・$d_{model}=128$・
warmupなしで見た崩壊と同じ特徴に見えたため，以降はこの仮説（容量の疑似的な
増大）を軸に検証した。

## $N=100$・warmup：直らない，顔ぶれが入れ替わるだけ

データ量は段階Aの最小値（50,000）に固定し，$d_{model}=32$，warmup{0, 5
エポック}を振った（`experiments/batch/run_n100_warmup_probe.sh`，段階Aと同じ
鍵5本）。

| 鍵 | warmup無し | warmup 5エポック |
| :--- | :---: | :---: |
| 20260927 | 0.2204 | 0.2148 |
| 20260928 | 0.1084 | **1.0000** |
| 20260929 | 0.2012 | 0.2094 |
| 20260930 | 0.2076 | 0.2118 |
| 20260931 | **0.5102** | 0.1086 |

: $N=100$・統制のwarmup有無による検証正解率（鍵5本）

離陸数（検証最大 >0.5）は**1/5→1/5で変わらず**，warmupは離陸する鍵の顔ぶれを
入れ替えただけだった（20260931が落ち，20260928が上がった）。$N=26$・
$d_{model}=128$でwarmupが系統的に直した（0/3→2/3）のとは異なる形である。

## $N=100$・学習率：下げても直らず，下げすぎると悪化する

「エポック0から完全に平坦」は学習率過大による初期の勾当の暴れが典型的な原因
であるため，学習率を1e-3（既定，既存データを流用）→3e-4→1e-4と下げた
（`experiments/batch/run_n100_lr_probe.sh`，他は段階Aと同条件，warmupなし）。

| 鍵 | lr=1e-3 | lr=3e-4 | lr=1e-4 |
| :--- | :---: | :---: | :---: |
| 20260927 | 0.2204 | 0.2146 | 0.2092 |
| 20260928 | 0.1084 | 0.1074 | 0.1118 |
| 20260929 | 0.2012 | 0.2086 | 0.2082 |
| 20260930 | 0.2076 | 0.2032 | 0.2040 |
| 20260931 | **0.5102** | **0.5130** | 0.1072 |

: $N=100$・統制の学習率ごとの検証正解率（鍵5本，warmupなし）

1e-3→3e-4はほぼ無変化（離陸鍵もそのまま）。1e-4までさらに下げると，唯一
離陸していた鍵まで床に落ちた（下げすぎるとむしろ悪化し，30エポック内で
収束しきれなくなったと見られる）。学習率過大説は支持されない。

## $N=100$・容量：増やしても直らず，むしろ収束が鈍る

実装を確認すると，Transformerへの入力系列長は$N$によらず常に14トークン
固定で，$N$が効くのは値の埋め込み（`Embedding(input_dim=N, output_dim=d_model)`）
が区別すべき記号数だと判明した。$N=26→100$で記号数が増えても$d_{model}$が
同じなら，1記号あたりに使える表現力（埋め込み容量）は変わらない。$N=26$での
「容量を増やしても有利にならない」という結論を$N=100$へ持ち込んではいけない，
という前週までの留保を踏まえ，$d_{model} \in \lbrace 64, 128\rbrace$×
warmup$\in \lbrace 0, 5\rbrace$を振った（`experiments/batch/run_n100_capacity_probe.sh`，
$d_{model}=32$は既存データを流用）。

| $d_{model}$ | warmup無し（離陸鍵） | warmup 5エポック（離陸鍵） |
| :--- | :--- | :--- |
| 32 | 1/5（20260931: 0.5102） | 1/5（20260928: 1.0000） |
| 64 | 0/5 | 1/5（20260928: 1.0000） |
| 128 | 0/5 | 1/5（20260928: 0.5022，部分的） |

: $N=100$・統制の容量×warmupごとの離陸鍵（鍵5本）

容量を増やしても離陸率は改善しない。むしろ$d_{model}=128$では収束が鈍る。
warmup 5エポック下で$d_{model}=32, 64$は鍵20260928を1.0000まで解けるが，
128では同じ鍵が0.5022止まりになる。残り4/5の鍵は$d_{model}$を32→64→128に
増やしても一度も床（~0.10〜0.22）から動かない。$N=100$では「容量が効くかも
しれない」という見込みは，この範囲（$d_{model} \le 128$）では支持されなかった。

## 見切りの判断

warmup・学習率・容量という，$N=26$で効いた3軸すべてを$N=100$統制に当てても，
**5鍵中4鍵は一度も床から動かず，残り1鍵の離陸は設定次第で入れ替わるだけ**
という同じパターンに収束した。これ以上この3軸を細かく探索しても，限られた
研究時間に見合う見込みが薄いと判断し，$N=100$へのスケーリングはここで一旦
停止する。

これは失敗ではなく境界の知見として扱う。実験C1の本線（$N=26$でself-attention
が$j$項の壁を破れるか）は，CNNに固有の帰納バイアスの問題であり，Transformerで
解消することを確認済みである。一方で$N=100$では，$j$項を持たない統制ですら
崩れる別の壁が現れた。つまり「$j$項の壁はアーキテクチャ依存（CNN固有）」と
「スケールの壁はアーキテクチャに依らず別に存在する」という，2つの異なる壁を
区別できたことがこの一連の実験の成果と言える。

# 方法論上の知見

今後の実験すべてに効くものだけを挙げる。

## 統制を外した検証は，容量×タスクの交互作用を見落とす

$d_{model}=128$の崩壊が$f_{2,2}$だけで測られていたら，「warmupで容量問題が
解決する」という単純な結論で終わっていた。統制$h$を同じ格子に含めたことで，
warmupが効くのは「容量×難しいタスク」の交互作用に限られ，容量そのものの
不安定性ではないと分かった。**容量や予算のような実験条件を振るときは，
必ず統制を同じ格子に含め，効果がタスク非依存かどうかを区別する。**

## 実装のパラメータ名が示す軸と，実際に変化する量は一致するとは限らない

「$N$を大きくすると系列長が伸びる」という直感は，この実装には当てはまらな
かった。`challenge_len`は全関数共通で14固定であり，$N$が実際に変えているのは
埋め込み層の語彙数である。**ハイパーパラメータを設計するときは，変数名から
推測せず，実装（特にモデル構築のコード）を読んで何が実際に変化するかを
確認する。**

## 「床にいるとき差が無いは効果の否定にならない」は，複数の軸を試した後にも当てはまる

今回はwarmup・学習率・容量という3つの軸を順に試したが，どれも「4/5鍵が
常に床」という同じ結果だった。1つの軸だけで見切りをつけず，複数の有力な軸を
実際に試した上で「見込みが薄い」と判断したことで，この見切りには根拠がある。
**見切りをつけるときは，有力な候補を複数実際に試したことを明示する。**

## 研究の枠組み

HCP（人間計算可能パスワード）とは，ユーザーが記憶する秘密の数表（以下「鍵」，各要素は0〜9の整数）と，暗算できる程度の簡単なアルゴリズムを使い，ランダムな入力（チャレンジ）から出力（レスポンス）を計算する認証方式である。本研究では，この「鍵をLLMがどこまで当てられるか／使いこなせるか」を測定するベンチマークとして再定義して扱っている。鍵と乱数シードから未知の問題を無限に生成できるため，事前学習データに答えが混入していないという利点がある。

研究は3つの経路で進めている：

1. 経路A（in-context推論）：LLMの重みは一切更新せず，プロンプトの中にいくつかの入出力example（チャレンジ→レスポンスの組）を見せて，その場で鍵を推論・逆算させる。

2. 経路B（ファインチューニング）：大量の入出力ペアを使い，追加学習（QLoRA）でLLMの重みに鍵とその使い方を覚え込ませる。従来の機械学習モデル（CNN）と同じ枠組みで，研究室の先行研究と直接比較できる。7月に一区切りとしたが，8月の指導教員の指示「より難しい関数の探索」を受けて再開している。

3. 経路C（1から学習する Transformer）：事前学習を持たない小さな Transformer エンコーダを，先行研究の CNN と同じデータ・同じ評価で学習させる。**先行研究との差分が self-attention だけになる**ため，アーキテクチャの効果だけを取り出せる。2026年9月に着手した。

3つの関係は次節の表に整理した。

## 実験の基本設定

1. **モデル**：ローカルで動かせる Qwen2.5-3B-Instruct を用い，QLoRA（4bit量子化＋LoRA）で追加学習している。

2. **Bパラダイム**：経路Bで採用している学習・評価形式。プロンプトはFew-shot例を含まない最小形式（「Input: [...] に対する Z を答えよ」のみ）とし，従来のCNNと同じ「入力→出力の直接対応のみを学習する」条件に揃えている。

3. **paradigm=pure**：教師データの形式。学習の答え（教師completion）は `{"answer": <値>}` というJSON1行のみで，計算の途中経過や鍵の値は一切含まない。損失もこの1行にしかかからず，プロンプト側（ルールの説明文を含む）には一切かからない。

4. **held-out評価**：学習に使ったデータとは別に生成した，一度も見せていない入力で正解率を測定する。学習用と評価用でチャレンジの乱数シード空間を分離しており，重複しないことを保証している。

5. **学習条件**：学習1000件・5エポックを標準としている（1000件という数は，比較対象であるCNNの学習データ量に揃えたもの）。

## 記号の定義（原論文の記法）

### 秘密写像 σ（＝本研究で「鍵」と呼んでいるもの）

$$
\sigma : [n] \to \mathbb{Z}_{10}
$$

$[n]$ は $1$ から $n$ までの自然数の集合 $\{1, 2, \dots, n\}$，$\mathbb{Z}_{10}$ は10で割った余りの同値類，すなわち1桁の整数の集合 $\{0, 1, \dots, 9\}$ である。つまり $\sigma$ は，画像や文字など n 個のオブジェクトから10進数の数字への写像であり，ユーザーはこれを暗記する。

### チャレンジ C

$$
C_i \in [n]^k
$$

$C_i$ は $i$ 番目のチャレンジ，$[n]^k$ は集合 $[n]$ の直積を $k$ 回とったもの，すなわち $[n]$ の要素を並べた長さ $k$ の列の全体である。

ここでの $k$ は「1回のチャレンジで提示するオブジェクトの個数」＝チャレンジ長であり，関数 $f$ が受け取る入力の個数と一致する（原論文は一般形を $f : \mathbb{Z}_{10}^k \to \mathbb{Z}_{10}$ と書く）。**この $k$ は，後述する関数族のパラメータ $k_1$・$k_2$ とは別のものである**。両者には $k = 10 + k_1 + k_2$ という関係がある。

### レスポンス

$$
f(\sigma(C))
$$

$\sigma(C)$ は，チャレンジ $C = (C_1, C_2, \dots, C_k)$ の各要素に秘密写像 $\sigma$ を適用したもの，すなわち $(\sigma(C_1), \sigma(C_2), \dots, \sigma(C_k))$ である。サーバは公開されたチャレンジを提示し，ユーザーは暗記した $\sigma$ で数字に直してから関数 $f$ を暗算し，その結果を答える。

## 本研究のパラメータと原論文の設定の対応

原論文で確認した内容である（2026-08）。

**本研究のパラメータと原論文の設定の対応**

| | 本研究 | 原論文 |
| :--------------- | :-----------: | :------------------------------------ |
| $n$（$\sigma$ のマス数） | 10 または 26 | 説明用の例示として n=26 を挙げるが，実験・公開チャレンジの主軸は n=50・100。著者自身は n=100 を約2時間で暗記したと報告 |
| $k$（チャレンジ長） | 14 | 14（入力変数は $10+k_1+k_2$ 個。$(k_1,k_2)$ が (1,3)(2,2)(3,1) のいずれでも14で揃う） |

プログラム中の `sgm` が $\sigma$，`X[i]` が $C_i$ にあたる。$n$ と $k$ は独立なパラメータであり，直接の関係はない。

なお原論文は n=26 を**安全性が不十分**と明示している（"the value n = 26 is too small to provide UF-RCA security even with small values of m"）。CSPソルバー攻撃（$f_{22}$）の結果は次の通りで，n=26 は全条件で破られている。

**CSPソルバー攻撃（$f_{22}$）による鍵の復元にかかる時間**

| n | m=50 | m=100 | m=1000 | m=10000 |
| :-----: | :------: | :------: | :------: | :------: |
| 26 | 23.5時間 | 40分 | 10分 | 2分 |
| 30 | HARD | UNSOLVED | 10分 | 20秒 |
| 50 | HARD | HARD | UNSOLVED | 7時間 |
| 100 | HARD | HARD | HARD | UNSOLVED |

したがって本研究が n=26 や n=10 を用いる理由は「安全な設定を再現するため」ではなく，**LLMの能力を測るベンチマークとして，差が観測できる難易度水準を選んだため**である。この区別は卒論で明記する必要がある。なお $n$ を大きくすると $\sigma$ の暗記負荷が上がるため，安全性と可用性は原理的にトレードオフの関係にある。

**Stage（情報開示レベル）**：0=ヒントなし，1=$\sigma$開示・ルール非開示，2=ルール（関数 $f$）は開示するが $\sigma$ は非開示，3=ルール開示＋$\sigma$の一部を開示。本研究は主にStage 2で行っている。

このStage 2という設定は恣意的なものではなく，**原論文の攻撃者モデルと厳密に一致する**（2026-08 に確認）。原論文の Password Unforgeability game（Definition 2）には *"The adversary is given the function f … and is shown the challenges"* と明記されており，「アルゴリズムは既知，鍵のみ秘密」というケルクホフスの原理に立脚した設定になっている。つまり本研究がルールを開示して鍵だけを隠すのは，原論文の安全性証明の前提そのものである。

## 人間計算可能関数 $f_{k_1,k_2}$

原論文が提案する関数族は次の形をしている。

$$f_{k_1,k_2}(x_0, x_1, \dots, x_{9+k_1+k_2})
   = x_j + \sum_{i=10+k_1}^{9+k_1+k_2} x_i \pmod{10}
$$

$$
\text{ここで}\quad j = \left( \sum_{i=10}^{9+k_1} x_i \right) \bmod 10
$$

入力変数は $10 + k_1 + k_2$ 個＝チャレンジ長 $k$ である。入力ベクトルは $x = (\sigma(C_0), \dots, \sigma(C_{9+k_1+k_2}))$，すなわちチャレンジに $\sigma$ を適用した後の数字列である。$k_1$ 個の項を足して添字 $j$ を作り（＝どこを見るかを決める），参照した値 $x_j$ にさらに $k_2$ 個の項を足して答えとする。先頭の10個（$x_0$〜$x_9$）は動的参照の飛び先として確保される（$j$ が $\bmod 10$ で決まるため）。

本研究の主対象 `func_22` は $(k_1, k_2) = (2, 2)$ の場合にあたる。

## 安全性パラメータ $s(f)$

原論文は，攻撃者が $\sigma$ を復元するのに必要な観測数が $m = \tilde{\Omega}(n^{s(f)})$ であると示しており，その指数 $s(f)$ を次のように定義している。

$$
s(f) = \min\left\{ \frac{r(f)}{2},\ g(f)+1 \right\}
$$

$r(f)$ は**分布的複雑度**，すなわち出力に偏り（相関）を生じさせないために固定しなければならない最小の入力変数数であり，提案関数では $r(f_{k_1,k_2}) = k_2 + 1$ である。$g(f)$ は**線形化変数数**，すなわち完全な線形方程式に退化させるために固定しなければならない最小の入力変数数であり，$g(f_{k_1,k_2}) = \min\{k_1, 10\}$ である。これを代入すると

$$
s(f_{k_1,k_2}) = \min\left\{ \frac{k_2+1}{2},\ k_1+1,\ 11 \right\}
$$

となり，`func_22` では $s(f) = 1.5$ である。

この $r(f)$ の定義「出力に偏りを生じさせないために固定すべき変数数」が $k_2+1$ であることは，**最後の加算項 $k_2$ が出力分布の偏りを打ち消す役割を担っている**ことを意味する。実験2 の結果は，この構造が実際に効いていることを示している（[experiment_index.md](../experiment_index.md)）。

## 難易度の分解と，扱っている関数の定義

本命の関数 `func_22` の難しさを3要素に分解し，簡単な要素から単独で検証できるよう診断用の関数を作成している。`sgm[i]` は鍵の i 番目，`X[i]` はチャレンジの i 番目を表す。

**難易度を3要素に分解した診断用の関数**

| 名称 | 計算式 | 分離している要素 |
| :--- | :--- | :--- |
| `lookup_k` | $Z = \text{sgm}[X_0]$ | ① 記憶のみ |
| `table_add_k` | $Z = (\text{sgm}[X_0] + \text{sgm}[X_1]) \bmod 10$ | ① + ② 合成 |
| `pointer_k` | $j = (\text{sgm}[X_{10}] + \text{sgm}[X_{11}]) \bmod 10$<br>$Z = \text{sgm}[X_j]$ | ① + ③ 動的参照 |
| `func_22`（本命） | $j = (\text{sgm}[X_{10}] + \text{sgm}[X_{11}]) \bmod 10$<br>$Z = (\text{sgm}[X_j] + \text{sgm}[X_{12}] + \text{sgm}[X_{13}]) \bmod 10$ | ① + ② + ③ |
| `table_add3_k` | $Z = (\text{sgm}[X_0] + \text{sgm}[X_1] + \text{sgm}[X_2]) \bmod 10$ | ① + ②（静的3項．統制） |
| `narrowptr_k_m1` | $j = (\text{sgm}[X_{10}] + \text{sgm}[X_{11}]) \bmod 1 = 0$<br>$Z = (\text{sgm}[X_j] + \text{sgm}[X_{12}] + \text{sgm}[X_{13}]) \bmod 10$ | 文面は動的・実質静的（統制） |
| `func_pow` | $Z = (\text{sgm}[X_{10}]^4 + 2\,\text{sgm}[X_{11}]^3 + 3\,\text{sgm}[X_{12}]^2 + 4\,\text{sgm}[X_{13}]) \bmod 10$ | 小川さんら Table 6 の no-j 統制そのもの |

「動的参照」とは，計算の途中で求めた数値 j を使ってチャレンジの j 番目の要素を新たに読みに行き，その値をさらに鍵で変換する，という間接参照の構造を指す。

## これまでの結果の要点（今回の報告の前提）

> [!WARNING]
> **7〜8月の結論の多くは撤回・保留になっている。**原因は関数の難しさではなく
> 測定系だった（9月13日の報告）。ここには現時点で保っている結論だけを書く。

1. **正解率が偶然水準付近でも「学習できない」とは言えない。**与えた学習予算の中で学習が**離陸したか**を測っていた。同じ関数・同じ鍵でもデータの引き方を変えると10.2% が 100% になる。
2. **1条件1run では何も言えない。**離陸は run ごとに起きるか起きないかであり，平均±標準偏差はその混合比を報告しているにすぎない。**離陸率**で報告する。
3. **偶然水準（10%）と比べてはいけない。**鍵ごとの**最頻値基準線**と比べる。
4. **鍵を揃えずに関数を比べてはいけない。**
5. ①記憶と②合成は，十分なデータ量があれば学習できる（未知の組み合わせでも汎化する）。
6. **③動的参照（$j$ 項）は，self-attention を与えると解ける。**経路C で$N=26$・50,000件の $f_{2,2}$ が検証 1.0000・試験 0.9998 に達した。小川さんらの CNN は同条件で最大 0.6858・平均 0.2872 であり，**「$j$ 項が構造的な壁」という先行研究の中心的結論はアーキテクチャ依存の主張に弱まる**。
7. **難しさは理論指標 $s(f)$ の順に並ばない（むしろ逆順）。**離陸率は$f_{3,1}$（$s=1.0$）4/20 ＜ $f_{1,3}$（$s=2.0$）11/20 ＜ $f_{2,2}$（$s=1.5$）15/20。
8. **離陸するかは，多くの場合鍵 $\sigma$ そのものの性質で決まる。**鍵5本 × 初期値4通りに分解すると，$f_{3,1}$ では鍵が分散の 100%，$f_{1,3}$ では 85% を説明する。
9. **崩壊点は観測密度にある。**鍵サイズを 26 → 50 にすると $f_{2,2}$ の離陸率は15/20 → 3/20 に落ちる（統制は 20/20 → 16/20）。
10. **鍵の効果は再現するが，$k_2$ 順に強まるという予測は反証された。**鍵20本に増やしても離陸率はC1（鍵5本）とほぼ一致する一方，エントロピーとの相関強度は予測した順序には並ばない（実験C2）。
11. **鍵の偏りが離陸率に効くかは，鍵ごとの基準線を統制して判定する必要がある。**最多重複は鍵ごとの基準線自体と強く相関しており（$f_{3,1}$ で $\rho=0.85$），固定しきい値による離陸判定だけを見ると見かけの相関が混ざる。
12. **基準線を実際に揃えた鍵集合でも，3関数すべてでエントロピーが離陸率に効き，最多重複は消える。**（実験C2.1）
13. **$N=26$で$d_{model}=128$の崩壊はwarmupで直るが，これは$j$項との相性に限られる。**統制はwarmupの有無に関わらず不変だった。
14. **$N=100$の統制は，データ量・warmup・学習率・容量のいずれを振っても解けなかった。**5鍵中4鍵は一度も学習が立ち上がらず，$N=100$へのスケーリングは一旦停止した（実験C1-N100）。

| 用語 | 意味 |
|---|---|
| 鍵 / $\sigma$ | 利用者が記憶する秘密の数表．長さ $n$，各要素は 0〜9 |
