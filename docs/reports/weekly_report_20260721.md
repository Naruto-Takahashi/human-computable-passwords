# 週次進捗報告（2026年7月7日〜7月21日）

対象: 「人間計算可能なパスワード（Human-Computable Passwords, HCP）」LLM推論限界評価

---

## 1. 前回までの流れ（経緯の整理）

1. **研究の枠組み（6月）**: HCPを「データ汚染のない推論ベンチマーク」として再定義し，情報開示レベル（Stage 0〜3）・ペア数 N・鍵部分開示数 K を振って，LLMの推論が崩壊から成功へ転じる**相転移境界**を測る計画を立てた。
2. **ファインチューニング実験（6月末〜7月上旬）**: QLoRAで鍵推論を試みたが，教師データへの鍵リーク（PoT）とモード崩壊（Pure，正解率5〜20%）に直面した。
3. **評価スクリプトのバグ発見（前回報告）**: `--provider lora` 時に stage 設定が強制的に0へリセットされ，学習条件と評価条件が食い違っていたことが判明。「ルール開示の効果なし」という結論は保留とした（バグ修正後の再検証結果は §3.2 で決着）。

今週は，これらの行き詰まりの**根本原因をコードレベルで総点検**し，研究計画の見直し（v2）とコードベースの全面リファクタリングを行った上で，**ファインチューニング実験を再設計・再実施**した。

## 2. Copilotレビュー（7/7）のご指摘への対応

### 指摘A: 「PoTリーク問題よりも simple_add での失敗の方が根本原因解明に近い」

**対応: コードベース監査で，ご指摘を裏づける問題を4件発見した。**

| # | 問題 | 影響 |
|---|---|---|
| 1 | FTの評価テストが学習データと重複（ホールドアウト不成立） | 従来の正解率5〜20%は「学習データ上での精度」だった |
| 2 | 「鍵復元率」が未実装（応答予測の正解率のみ） | 鍵の逆推定を直接測る手段がなかった |
| 3 | 全実験が単一の鍵（seed=42） | 複数鍵での反復（成功率の測定）が不可能だった |
| 4 | アルゴリズム定義が4ファイルに重複 | PoT鍵リークの温床になっていた |

（詳細: `docs/refactor_notes.md`）

### 指摘B（優先度1）: 「教師データを目視確認せよ」（tokenizer / EOS / JSON整形 / ラベルマスクの不具合を疑う）

**対応: 目視の代わりに定量的根拠を積み重ね，パイプラインは健全であることを確定させた。**

まず旧実験の学習曲線（loss≈0.19, token_accuracy≈0.93 で横ばい）を検証したところ，「JSON書式は完全に学習し，答えの数字1トークンだけが偶然水準」という仮定の理論値と定量的に一致した。この時点では「不具合ではなく教師信号不足を示唆する」という推測に留まっていたが，その後の実験で確定に切り替わった：

- **過学習テスト（指摘C）**: 20件を完全暗記（20/20正解）。パイプラインが壊れていれば起こり得ない結果であり，tokenizer / EOS / JSON整形 / ラベルマスクはすべて正常に機能していることを直接示す。
- **除外ペア実験（§3.2）**: 学習で一度も見せていない入力の組でも99%正解。データの受け渡し・ラベル付けが正しくなければ，見せていない入力への汎化は起こり得ない。

以上により，**指摘Bは「不具合なし」で確定的に決着した**。

### 指摘C（優先度2）: 「train=20件の過学習テストを最優先で実施せよ」

**対応: 実施・合格。** 20件を完全暗記（token_accuracy=1.0，学習セット上で20/20正解）。**パイプラインは健全**と確定した。

### 指摘D（優先度3）: 「最小問題（(X0 + secret) % 10）で秘密鍵推論の可否を検証せよ」

**対応: ご提案どおり実装・実施し，成功した。** ルール開示・鍵1桁（`secret_add`）で **held-out 正解率100%**。「SFTでは鍵が重みに入らない」という前回までの見立ては誤りで，旧モード崩壊の主因はタスクの困難さではなく旧設計の欠陥（指摘Aの4件）だったと判明した。

## 3. 今週の成果

### 3.1 研究計画をv2へ改訂・コードベースを全面リファクタリング

研究の主軸を，**「情報理論的に解ける領域で，LLMは実際どこから解けるようになるか」**の測定に再定式化した（`docs/plan.md`）。厳密ソルバーで「鍵が一意に定まるペア数」「実際に鍵を計算機的に復元できること」を基準線として持たせることで，LLMが失敗しても「情報不足」「計算不能」と切り分けた上での結果として成立する設計にした。あわせてコードを全面刷新し，鍵復元タスクの新実装・複数鍵での反復・プロンプト保存などを整備した（詳細: `docs/refactor_notes.md`）。

### 3.2 ファインチューニング実験の結論：「ポインタ間接参照」だけが本質的に学習できない

指摘A〜Dへの対応を踏まえ，FT実験を「Few-shot例なし・CNNと同条件」で再設計し，難易度を3段階に分けて学習可能性を調べた。

| 何を学習させるか | LLM (Qwen2.5-3B QLoRA) | CNN |
|---|---|---|
| 生入力の算術規則（simple_add） | **100%** | 10%（偶然水準） |
| 秘密鍵1桁 | **100%** | 94% |
| 秘密テーブルの参照のみ（26マス） | **100%** | 100% |
| テーブル参照2回＋mod和（26マス） | 崩壊 → **データ量を増やすと100%まで回復** | 51% |
| テーブル参照＋**ポインタ**（間接参照，本来のHCP） | **12%（データを5倍にしても不変）** | 7% |

**結論**:

1. 鍵テーブルの記憶量そのものは壁ではない（26マス完全に学習可能）。
2. 「参照した値を足し合わせる」程度の合成も，データ量を増やせば学習できる（崩壊は能力の限界ではなくデータ不足だった）。**この合成が丸暗記でなく真の計算獲得であることも実証済み**（下記の追加検証）。
3. **唯一学習できなかったのは，参照先が入力によって動的に変わる「ポインタ間接参照」**。データを5倍にしても正解率は偶然水準のまま動かず（6.5〜8.0%），二項検定で偶然（10%）と統計的に区別できないことを n_test=200 で確認した。
4. LLMとCNNは得意分野が逆転する：既知の演算（足し算）の再利用はLLMが圧勝，未知のテーブルを丸ごと近似するのはCNNの方が粘る。
5. **§1で保留にしていた「ルール開示の効果」も決着**：ポインタ間接参照は，ルールを開示（Stage 2）してもしなくても（Stage 0）正解率12%で変わらなかった。バグ修正済みの条件での再検証であり，「ルールを教えても鍵の逆算は助けにならない」と結論できる。

**追加検証：「合成」は丸暗記ではなく真の計算獲得だった**

上記2の成功が「表を丸ごと暗記しただけ」ではないかという疑念を検証するため，(X0,X1) の組50個を学習データから完全に除外し，学習後に**その除外した組だけ**で評価した。結果は **99%（99/100）**——通常のheld-out評価（100%）とほぼ同じ精度で，一度も見ていない組み合わせにも正しく対応できていた。これにより，②の合成が丸暗記ではなく汎化可能な計算獲得であることが実証された。

**位置づけ**: 先輩方のCNN研究との公平比較という当初の目的を達成し，「LLMの学習が本質的に苦手とするのはHCPの何か」を特定できた。①記憶・②合成は真に獲得可能，③ポインタのみ本質的な壁——という結論が実験的に固まったため，この一連の実験（過学習テスト→最小タスク→難易度ラダー→データ量追試→除外ペア検証）で**ファインチューニング路線は一区切りとする**。8月からは本丸（下記）に注力する。

## 4. 次にやること（Next Actions）

研究の主眼は，**プロンプト内の例だけを見せて，その場で鍵を推論させる（in-context推論）実験**に移る。これが当初計画していた相転移境界の測定そのものであり，8月からの本実験にあたる。

1. 情報理論的な基準線（何ペア見せれば鍵が一意に定まるか）を全アルゴリズムで算出する。
2. ローカルLLM（7B/14B）に対し，見せるペア数 N を段階的に増やしながら鍵復元をさせ，どこから成功し始めるかを測る（複数の鍵で反復し，成功率として集計）。
3. 鍵の一部を先に開示した場合の効果も同様にスキャンする。
4. 結果を商用モデルとも比較する。

保留事項（余力があれば）: モデル規模を変えた追試，境界条件の複数鍵シード反復。
