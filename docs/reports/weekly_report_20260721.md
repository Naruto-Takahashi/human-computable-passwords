# 週次進捗報告（2026年7月7日〜7月21日）

対象: 「人間計算可能なパスワード（Human-Computable Passwords, HCP）」LLM推論限界評価

---

## 0. この一週間で何をしたか（要約）

HCP（秘密の数表＝「鍵」を使った暗算パズル）を，LLM に**追加学習（ファインチューニング）** させて解かせる実験をやり直した。前回までは「学習させても鍵を覚えられない」という結果が出ていたが，これは**実験の作り方に不具合があったから**であって，LLM の能力の問題ではないことが判明した。不具合を直した上で，パズルの難しさを1段階ずつ足しながら再実験したところ，次のことが分かった。

> **「表を覚える」「覚えた値を組み合わせて計算する」はLLMでも学習できる。唯一学習できなかったのは「参照する場所自体が入力によって変わる（動的参照）」という要素だけだった。**

以下，詳細を述べる。

---

## 1. 前回までの流れ（経緯の整理）

1. **研究の枠組み（6月）**: HCPを「データ汚染のない推論ベンチマーク」として再定義し，LLMがどこまでこのパズルを解けるかの限界を測る計画を立てた。
2. **ファインチューニング実験（6月末〜7月上旬）**: 鍵を覚えさせようとしたが，2つの問題が起きた。
   - 学習用の「模範解答」に，答えの鍵の値がそのまま書き込まれていた（カンニング教材を渡していたのと同じで，見かけ上100%正解できても無意味だった）。
   - もう一方のやり方では，学習させても正解率が5〜20%程度にしかならず，しかも予測がいつも同じ数字に偏る「崩壊」が起きた。
3. **評価スクリプトのバグ発見（前回報告）**: 学習済みモデルを評価するプログラムに設定ミスがあり，「学習させた条件」と「評価した条件」が食い違っていたことが判明。このため「崩壊」の原因がまだ特定できていなかった。

今週は，この行き詰まりの**根本原因をコードレベルで洗い直し**，実験を作り直した上で，改めてファインチューニングを実施した。

---

## 2. Copilotレビュー（7/7）のご指摘への対応

### 指摘A: 「鍵の値が書き込まれていた問題より，シンプルな足し算ですら失敗した方が本質的な原因究明に近いのでは」

**対応: コード全体を点検し，実験の作り方自体に4つの不具合を発見した。**

一番重要な不具合はこれ：**学習に使った問題と，正解率を測るためのテスト問題が，実は同じものだった**。試験勉強で使った問題集と，本番の試験問題が全く同じだった，というような状態で，これでは「本当に理解して解けるようになったか」を測れていない。これに加えて，(a) 「鍵を正しく当てられたか」を直接測る仕組みがなかった，(b) 毎回同じ1つの鍵しか使っておらず，たまたまその鍵が難しかっただけの可能性を排除できていなかった，(c) パズルの計算ルールを書いたコードが4箇所にバラバラにあり，直しきれない構造だった，という問題も見つかった。（詳細: `docs/refactor_notes.md`）

### 指摘B（優先度1）: 「学習に使ったデータを実際に目で見て，作り方に不具合がないか確認せよ」

**対応: 目視の代わりに，実験結果から間接的に確認し，その後の追加実験で確定させた。**

まず，崩壊していたときの数字のクセ（どのくらい正しく学習できているかを示す指標が，ある値で頭打ちになっていた）を調べたところ，「答えの書式（JSON の書き方など）は完璧に覚えているが，肝心の答えの数字だけが当てずっぽう」という状態と一致することが分かった。これは「プログラムが壊れている」というより「学習のさせ方の問題で，数字を覚えるための手がかりが足りていない」ことを示唆していた。

この推測は，のちの2つの実験で裏付けられた。1つは20問だけを繰り返し学習させる**丸暗記テスト**（下記）で，完璧に20問とも正解できた——プログラムが壊れていればこれもできないはずである。もう1つは，学習で一度も見せていない問題だけを集めて解かせた**未知問題テスト**（下記）で，99%正解できた——これもデータの受け渡しが壊れていれば起こり得ない。この2つにより，**学習の土台（データの作り方，プログラム側の処理）に不具合はない**と確定した。

### 指摘C（優先度2）: 「20問だけを繰り返し学習させ，丸暗記できるか試せ」

**対応: 実施・合格。** 20問を完璧に覚えられた（学習に使った20問全問正解）。これで学習の仕組み自体は正常に動いていることを確認できた。

### 指摘D（優先度3）: 「(最初の入力 + 秘密の1桁の数) を10で割った余り」のような超シンプルな問題で，秘密の値を学習できるか試せ

**対応: ご提案どおり実施し，成功した。** 計算のルールは教え，秘密の1桁だけを伏せて200問学習させたところ，学習で見せていない問題でも100%正解できた。つまり，「LLMは学習では秘密の値を覚えられない」という前回までの見立てはそもそも誤りで，前回の崩壊は，指摘Aで見つかった実験の作り方のバグが原因だったと分かった。

## 3. 今週の本実験：パズルの難しさを1段階ずつ足して，どこまで学習できるかを調べた

### 3.1 実験のやり方

指摘A〜Dへの対応を踏まえ，先輩方の従来手法（CNN，画像認識などにも使われるニューラルネットワーク）と条件を揃えた上で，本命のパズル（`func_22`）が持つ「難しさ」を3つの要素に分解し，簡単な要素から順に1つずつ足しながら，LLMに学習させて正解率を測った。

- **要素①「記憶」**: 秘密の数表（26マスの表）から，指定された場所の値を答えるだけ。表を覚えていれば解ける。
- **要素②「合成」**: 表から2箇所の値を取り出し，その2つを足して1桁にする。表を覚えた上で，さらに足し算を組み合わせる必要がある。
- **要素③「動的参照（本命の難しさ）」**: 「どこを参照するか」自体が，別の場所の値によって変わる。人間で言えば，「まず2つの数字を足してその答えの番号のマスを見に行き，そのマスの値を使って計算する」という，参照先が一意に定まらない構造。

**要素③の具体例**（実際に使った鍵と問題）：

```
秘密の表（26マス）: [8, 6, 5, 2, 3, 0, 0, 0, 1, 8, 6, 9, 5, 6, 9, 7, 6, 5, 5, 9, 2, 8, 6, 0, 3, 8]

問題: 「11番目の数字」と「12番目の数字」を見て、表から値を2つ引いて足す
       → 11番目の数字=14 → 表[14]=9
       → 12番目の数字=1  → 表[1]=6
       → 9+6=15 → 下1桁の「5」が「次にどのマスを見るか」を決める番号になる
問題文の5番目の数字を見る → 5番目の数字=14 → 表[14]=9 ←これが「参照先」の値
最後に、13番目・14番目の数字を表で引いた値も足す：表[15]=7, 表[25]=8
答え = 9 + 7 + 8 = 24 → 下1桁の「4」が正解
```

このように，**「どこを見るか」を計算した結果で決めてから，改めてそこを見に行く**という2段階の間接参照が③の本質である。

### 3.2 結果

Few-shot例なし（学習だけを頼りに解かせる条件）で，従来手法（CNN）と同じデータ量（1000件）を使って比較した。

| 難しさ | 具体的な課題 | LLM（学習させた） | CNN（先輩方の従来手法） |
|---|---|---|---|
| （基準）秘密要素なしの単純な足し算 | 入力の数字を3つ足すだけ | **100%** | 10%（当てずっぽうと同水準） |
| （基準）秘密の値1個だけ | 入力に秘密の1桁を足す | **100%** | 94% |
| ①記憶のみ | 26マスの表から1箇所を答える | **100%** | 100% |
| ①+②記憶＋合成 | 表から2箇所引いて足す（26マス） | 崩壊 → **データを増やすと100%まで回復** | 51% |
| ①+②+③記憶＋合成＋動的参照 | 本命の `func_22` | **12%（当てずっぽうと同水準，データを5倍にしても変わらず）** | 7% |

### 3.3 分かったこと

1. **「表を覚えること」自体は問題にならない**：26マス全部を正しく覚えられた。
2. **「合成」も，データの量を増やせば克服できた**：最初は崩壊したが，これは能力の限界ではなく，練習量（見せる問題数）が足りなかっただけだった。データを5倍に増やしたら崩壊は解消し，100%正解できるようになった。
3. **「合成」の成功は丸暗記ではないことを確認した**：②の成功が「大量の答えパターンをまるごと暗記しただけ」ではないかという疑いを検証するため，特定の入力の組み合わせ50通りを学習から完全に除外し，**その除外した50通りだけ**で改めてテストした。結果は99%正解——見たことのない組み合わせにも正しく対応できており，本当に「表を引いて足す」という計算のやり方自体を身につけていたことが確認できた。
4. **唯一，克服できなかったのが「動的参照」**：本命の `func_22` は，データを5倍に増やしても正解率12%（当てずっぽうと同じ水準）のまま変化しなかった。合成のときはデータを増やせば直ったのと対照的に，動的参照だけはデータ量では解決しなかった。
5. **LLMとCNNは得意・不得意が逆**：単純な足し算（表を使わない）はLLMが圧勝，CNNはほぼ当てずっぽう。逆に大きな表を丸ごと近似する課題ではCNNの方が粘り強い。

### 3.4 位置づけ

先輩方のCNN研究と条件を揃えた比較という当初の目的を達成した上で，「LLMの学習が本質的に苦手とするのは，HCPのどの要素なのか」を具体的に特定できた。①記憶と②合成は，データ量さえあれば正しく学習できる。③動的参照だけが，データを増やしても解決しない壁として残った。

以上をもって，この一連の実験（丸暗記テスト → 秘密の値1個のテスト → 難易度を段階的に上げたテスト → データ量を変えた追試 → 丸暗記でないことの確認）で，**ファインチューニング実験は一区切りとする**。8月からは，学習させずにプロンプトの例だけを見せて，その場で鍵を推論させる実験（本来の研究計画の本丸）に注力する。

## 4. 次にやること（Next Actions）

研究の主眼は，**プロンプト内に例をいくつか見せて，その場で秘密の鍵を推論させる実験**に移る。これが当初計画していた「LLMの推論がどこから成功し始めるか」を測る，本来の研究の本丸にあたる。

1. 「何個の例を見せれば，理論上，鍵が一意に決まるか」を先に計算しておく（これが比較の基準線になる）。
2. ローカルLLM（7B/14B）に，見せる例の数を少しずつ増やしながら鍵を当てさせ，どのあたりから正解し始めるかを調べる（複数の鍵で繰り返し試し，成功率として集計する）。
3. 鍵の一部だけを先に教えた場合の効果も同様に調べる。
4. 結果を商用モデル（Gemini等）とも比較する。

保留事項（余力があれば）: モデルの大きさを変えた追試，境界付近の追加検証。
