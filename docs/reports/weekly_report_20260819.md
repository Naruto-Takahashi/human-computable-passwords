## 1.1 研究の枠組み

HCP（人間計算可能パスワード）とは，ユーザーが記憶する秘密の数表（以下「鍵」，各要素は0〜9の整数）と，暗算できる程度の簡単なアルゴリズムを使い，ランダムな入力（チャレンジ）から出力（レスポンス）を計算する認証方式である。本研究では，この「鍵をLLMがどこまで当てられるか／使いこなせるか」を測定するベンチマークとして再定義して扱っている。鍵と乱数シードから未知の問題を無限に生成できるため，事前学習データに答えが混入していないという利点がある。

研究は2つの経路で進めている：

1 経路A（in-context推論）：LLMの重みは一切更新せず，プロンプトの中にいくつかの入出力example（チャレンジ→レスポンスの組）を見せて，その場で鍵を推論・逆算させる。

2 経路B（ファインチューニング）：大量の入出力ペアを使い，追加学習（QLoRA）でLLMの重みに鍵とその使い方を覚え込ませる。従来の機械学習モデル（CNN）と同じ枠組みで，研究室の先行研究と直接比較できる。7月に一区切りとしたが，8月にご指示いただいた「より難しい関数の探索」を受けて再開している。今週の報告はこちらである。

## 1.2 実験の基本設定

1 **モデル**：ローカルで動かせる Qwen2.5-3B-Instruct を用い，QLoRA（4bit量子化＋LoRA）で追加学習している。

2 **Bパラダイム**：経路Bで採用している学習・評価形式。プロンプトはFew-shot例を含まない最小形式（「Input: [...] に対する Z を答えよ」のみ）とし，従来のCNNと同じ「入力→出力の直接対応のみを学習する」条件に揃えている。

3 **paradigm=pure**：教師データの形式。学習の答え（教師completion）は `{"answer": <値>}` というJSON1行のみで，計算の途中経過や鍵の値は一切含まない。損失もこの1行にしかかからず，プロンプト側（ルールの説明文を含む）には一切かからない。

4 **held-out評価**：学習に使ったデータとは別に生成した，一度も見せていない入力で正解率を測定する。学習用と評価用でチャレンジの乱数シード空間を分離しており，重複しないことを保証している。

5 **学習条件**：学習1000件・5エポックを標準としている（1000件という数は，比較対象であるCNNの学習データ量に揃えたもの）。

## 1.3 記号の定義（原論文の記法）

**秘密写像 σ**（＝本報告で「鍵」と呼んでいるもの）

```
σ : [n] → Z₁₀
```

`[n]` は 1 から n までの自然数の集合 {1, 2, …, n}，`Z₁₀` は10で割った余りの同値類，すなわち1桁の整数の集合 {0, 1, …, 9} である。つまり σ は，画像や文字など n 個のオブジェクトから10進数の数字への写像であり，ユーザーはこれを暗記する。

**チャレンジ C**

```
Cᵢ ∈ [n]ᵏ
```

`Cᵢ` は i 番目のチャレンジ，`[n]ᵏ` は集合 `[n]` の直積を k 回とったもの，すなわち `[n]` の要素を並べた長さ k の列の全体である。

ここでの k は「1回のチャレンジで提示するオブジェクトの個数」＝チャレンジ長であり，関数 f が受け取る入力の個数と一致する（原論文は一般形を `f : Z₁₀^k → Z₁₀` と書く）。**この k は，後述する関数族のパラメータ k₁・k₂ とは別のものである**。両者には `k = 10 + k₁ + k₂` という関係がある。

**レスポンス**

```
f(σ(C))
```

`σ(C)` は，チャレンジ `C = (C₁, C₂, …, C_k)` の各要素に秘密写像 σ を適用したもの，すなわち `(σ(C₁), σ(C₂), …, σ(C_k))` である。サーバは公開されたチャレンジを提示し，ユーザーは暗記した σ で数字に直してから関数 f を暗算し，その結果を答える。

## 1.4 本研究のパラメータと原論文の設定の対応

今週，原論文で確認した内容である。

| | 本研究 | 原論文 |
| :-: | :-: | :-: |
| n（σ のマス数） | 10 または 26 | 説明用の例示として n=26 を挙げるが，実験・公開チャレンジの主軸は n=50・100。著者自身は n=100 を約2時間で暗記したと報告 |
| k（チャレンジ長） | 14 | 14（入力変数は `10+k₁+k₂` 個。`(k₁,k₂)` が (1,3)(2,2)(3,1) のいずれでも14で揃う） |

プログラム中の `sgm` が σ，`X[i]` が `Cᵢ` にあたる。n と k は独立なパラメータであり，直接の関係はない。

なお原論文は n=26 を**安全性が不十分**と明示している（"the value n = 26 is too small to provide UF-RCA security even with small values of m"）。CSPソルバー攻撃（f₂₂）の結果は次の通りで，n=26 は全条件で破られている。

| n | m=50 | m=100 | m=1000 | m=10000 |
| :-: | :-: | :-: | :-: | :-: |
| 26 | 23.5時間 | 40分 | 10分 | 2分 |
| 30 | HARD | UNSOLVED | 10分 | 20秒 |
| 50 | HARD | HARD | UNSOLVED | 7時間 |
| 100 | HARD | HARD | HARD | UNSOLVED |

したがって本研究が n=26 や n=10 を用いる理由は「安全な設定を再現するため」ではなく，**LLMの能力を測るベンチマークとして，差が観測できる難易度水準を選んだため**である。この区別は卒論で明記する必要がある。なお n を大きくすると σ の暗記負荷が上がるため，安全性と可用性は原理的にトレードオフの関係にある。

**Stage（情報開示レベル）**：0=ヒントなし，1=σ開示・ルール非開示，2=ルール（関数 f）は開示するが σ は非開示，3=ルール開示＋σの一部を開示。本研究は主にStage 2で行っている。

このStage 2という設定は恣意的なものではなく，**原論文の攻撃者モデルと厳密に一致する**ことを今週確認した。原論文の Password Unforgeability game（Definition 2）には *"The adversary is given the function f … and is shown the challenges"* と明記されており，「アルゴリズムは既知，鍵のみ秘密」というケルクホフスの原理に立脚した設定になっている。つまり本研究がルールを開示して鍵だけを隠すのは，原論文の安全性証明の前提そのものである。

## 1.5 人間計算可能関数 f_{k₁,k₂}

原論文が提案する関数族は次の形をしている。

```
f_{k₁,k₂}(x₀, x₁, …, x_{9+k₁+k₂})  =  x_j + Σ[i=10+k₁ … 9+k₁+k₂] xᵢ   (mod 10)

              ここで   j  =  ( Σ[i=10 … 9+k₁] xᵢ )   (mod 10)
```

入力変数は `10 + k₁ + k₂` 個＝チャレンジ長 k である。入力ベクトルは `x = (σ(C₀), …, σ(C_{9+k₁+k₂}))`，すなわちチャレンジに σ を適用した後の数字列である。k₁ 個の項を足して添字 j を作り（＝どこを見るかを決める），参照した値 x_j にさらに k₂ 個の項を足して答えとする。先頭の10個（x₀〜x₉）は動的参照の飛び先として確保される（j が mod 10 で決まるため）。

本研究の主対象 `func_22` は `(k₁, k₂) = (2, 2)` の場合にあたる。

## 1.6 安全性パラメータ s(f)

原論文は，攻撃者が σ を復元するのに必要な観測数が `m = Ω̃(n^s(f))` であると示しており，その指数 s(f) を次のように定義している。

```
s(f) = min{ r(f)/2 ,  g(f)+1 }
```

r(f) は**分布的複雑度**，すなわち出力に偏り（相関）を生じさせないために固定しなければならない最小の入力変数数であり，提案関数では `r(f_{k₁,k₂}) = k₂ + 1` である。g(f) は**線形化変数数**，すなわち完全な線形方程式に退化させるために固定しなければならない最小の入力変数数であり，`g(f_{k₁,k₂}) = min{k₁, 10}` である。これを代入すると

```
s(f_{k₁,k₂}) = min{ (k₂+1)/2 ,  k₁+1 ,  11 }
```

となり，`func_22` では s(f) = 1.5 である。

この r(f) の定義「出力に偏りを生じさせないために固定すべき変数数」が `k₂+1` であることは，**最後の加算項 k₂ が出力分布の偏りを打ち消す役割を担っている**ことを意味する。今週の結果（3節）は，この構造が実際に効いていることを示している。

## 1.7 難易度の分解と，扱っている関数の定義

本命の関数 `func_22` の難しさを3要素に分解し，簡単な要素から単独で検証できるよう診断用の関数を作成している。`sgm[i]` は鍵の i 番目，`X[i]` はチャレンジの i 番目を表す。

| 名称 | 計算式 | 検証する要素 |
| :-: | :-: | :-: |
| lookup\_k | Z = sgm\[X0\] | ①記憶：表を正しく参照できるか |
| table\_add\_k | Z = (sgm\[X0\] + sgm\[X1\]) mod 10 | ①+②合成：2箇所参照して足す |
| pointer\_k | j = (sgm\[X10\]+sgm\[X11\]) mod 10 ; Z = sgm\[X\[j\]\] | ③動的参照のみを単独抽出 |
| func\_22（本命） | j = (sgm\[X10\]+sgm\[X11\]) mod 10 ; Z = (sgm\[X\[j\]\] + sgm\[X12\] + sgm\[X13\]) mod 10 | ①+②+③すべて |

「動的参照」とは，計算の途中で求めた数値 j を使ってチャレンジの j 番目の要素を新たに読みに行き，その値をさらに鍵で変換する，という間接参照の構造を指す。

## 1.8 8月にご指示いただいた課題と，追加した関数

8月に「人間計算可能性を少し犠牲にしても，動的参照構造を増やす方向でLLMの限界を探る」というご指示をいただき，ご共有いただいた資料（8/1）で挙げられていた候補のうち，優先度の高い3種類を実装した。いずれも本命の `func_22`（動的参照が1本）を出発点に，**動的参照の本数や繋ぎ方を変えた**ものである。

**pointer\_chain（深さ方向・直列に反復）**

```
j = (鍵[X10] + 鍵[X11]) mod 10
j ← 鍵[X_j]                  … これを (深さ-1) 回くりかえす
Z = 鍵[X_j]
```

同じ操作「指した先を見て，その値が示す位置をまた指す」を繰り返す。深さ1は既存の `pointer_k` と一致する。**足し算を含まない**（k₂=0）のは，深さの効果だけを取り出すためである。今週まで実験してきたのはこれである。

**dualptr（並列・独立な2本）**

```
j1 = (鍵[X10] + 鍵[X11]) mod 10
j2 = (鍵[X12] + 鍵[X13]) mod 10     … j1 とは無関係に決まる
Z  = (鍵[X_j1] + 鍵[X_j2]) mod 10
```

動的参照を2本に増やすが，**互いに依存しない**。2箇所を別々に見に行って足す形なので，反復（前の結果を次の入力にする）は含まない。資料では「最大候補（私の本命）」と位置づけられていた。

**recptr（直列・依存あり）**

```
j1 = (鍵[X10] + 鍵[X11]) mod 10
j2 = (鍵[X_j1] + 鍵[X12]) mod 10    … j1 の参照結果が j2 の計算に入る
Z  = (鍵[X_j2] + 鍵[X13]) mod 10
```

2本目のポインタ `j2` を求めるのに1本目の参照結果 `鍵[X_j1]` を使うため，**参照同士に依存関係がある**。`func_22` の依存を一段強めた形にあたる。`pointer_chain` と似ているが，**各段で新しい項（X12，X13）を足す**点が決定的に異なる（3.3節）。

| 名称 | 動的参照の本数 | 参照どうしの関係 | 末尾の足し算 |
| :-: | :-: | :-: | :-: |
| func\_22（基準） | 1本 | — | あり |
| pointer\_chain | 深さ分（直列） | 前の結果が次の入力 | **なし** |
| dualptr | 2本 | 独立（依存なし） | あり |
| recptr | 2本 | 依存あり | あり |

今週までに実験したのは `pointer_chain`（深さ）のみである。`dualptr`・`recptr` は実装済みだが未実験であり，これが次にやることになる（5節）。

# 3 今週の結果

## 3.1 評価方法に誤りがあり，先週までの結論が覆った

深さ1・2・3を比較する実験を行い，当初「深さの効果は確認できない」と結論していた。しかし**評価の件数が50件では粗すぎた**ことに気づいた。50件では約27ポイント以上の差しか検出できず，深さ間で見ていた差（12〜18ポイント）は原理的に判定不能だったためである。

評価にかかる時間は50件で82秒（学習は約2時間）と，学習の90分の1でしかない。そこで学習済みモデル8個を**再学習なしで500件で評価し直した**ところ，結論が変わった。

**評価件数500件での正解率**

| 鍵 | 深さ1 | 深さ2 | 深さ3 |
| :-: | :-: | :-: | :-: |
| 鍵A | 24.8% | 24.2% | **31.6%** |
| 鍵B | 35.8% | 35.6% | **44.0%** |

深さ1と深さ2は両方の鍵でほぼ完全に一致し（差は0.6ポイント以内，有意差なし），深さ3だけが両方の鍵とも約8ポイント高い（両鍵をまとめた検定で p < 0.001）。50件で測っていたときは点推定が最大13ポイントずれており，「2つの鍵で挙動が逆方向」という見かけ上の矛盾が生じていた。正しく測ると，独立した2つの鍵で同じ現象が再現している。

なお**方向は当初の予測とは逆**である。「深さが増すほど劣化する」ではなく「深さ3で上昇」した。

## 3.2 原因は関数設計の欠陥だった（不動点）

なぜ深いほど簡単になるのかを調べ，原因を特定した。

`pointer_chain` は `j ← 鍵[X_j]` という参照を繰り返す。ここで **`鍵[X_j]` がたまたま j 自身と同じ値になると，ポインタはそこから動けなくなる**（不動点）。そしてこのとき `答え = 鍵[X_j] = j` となり，**答えがポインタの値そのものに一致する**という自明な関係に退化する。実データで確認したところ，停止した事例の**100%（216件中216件）**がこの関係を満たしていた。

反復を重ねるほどこの状態に捕まる確率は上がる（鍵Bでは深さ2の10%から深さ3の25%へ）。つまり**深さは難易度を単調に上げる変数として機能しておらず，むしろ自明な問題を増やしていた**。

さらに検証したところ，次のことが分かった。

1 不動点の**発生確率は足し算を加えても変わらない**（26.1%→26.1%）。有限集合の上で写像を反復すれば必ず循環に入るため，数学的に避けられない。

2 ただし足し算があると，不動点に落ちても答えは自明にならない（自明化率100%→12.8%）。つまり**足し算は不動点の発生を防ぐのではなく，落ちても問題が壊れないよう保護する働き**をしている。これは 1.6節 の r(f) = k₂+1 という構造の，もう一つの現れ方である。

3 真の原因は「**同じ写像を反復していること**」だった。一度止まると100%抜けられないためである。各ステップで異なる入力を使えば抜けられるようになり，深さを増やしても自明な事例は増えない（12%で頭打ち）。

## 3.3 この欠陥は深さ方向に固有であり，dualptr・recptr は影響を受けない

上記を踏まえ，未実験の2つの関数に同じ欠陥がないかを20万件のランダムチャレンジで確認した（鍵Bを使用）。

| 関数 | ポインタが停止する割合 | 停止時に答えが自明化する割合 | 答えの値の種類 |
| :-: | :-: | :-: | :-: |
| pointer\_chain（深さ3） | 26.0% | **100.0%** | 7 |
| recptr（直列・依存あり） | 11.5% | 16.5% | **10** |
| dualptr（並列・独立2本） | 11.5% | 16.6% | **10** |

**`recptr` と `dualptr` には，この欠陥がない。**

理由は明快である。`recptr` は各段で新しい項を足す形（`j2 = (鍵[X_j1] + X12) mod 10`，`Z = (鍵[X_j2] + X13) mod 10`）になっており，同じ写像の反復ではない。`dualptr` はそもそも反復を含まない。両者とも最後に足し算があるため，答えの値の種類も10（鍵に含まれる全ての数字）に保たれ，鍵の偏りが答えに漏れる問題も生じない。

つまり**8月に検証した3候補のうち，最も脆弱な1つを先に選んでいた**ことになる。残る2つはそのまま実験できる状態にある。

## 3.4 他の候補（XOR型・条件分岐型）を採らない理由

ご共有いただいた資料では，上記3つに加えて XOR型・条件分岐型も挙げられていた（優先順位は4位・5位）。それぞれ次の理由から，当面は採らない方がよいと判断した。

**条件分岐型**（`x_j < 5` なら `Z=(X12+X13)`，そうでなければ `Z=(x_j+X12+X13)`）には，不動点と同種の抜け道がある。20万件で測ると**70%の事例で答えが動的参照の結果に一切依存しない**（`x_j < 5` の側に落ちるため）。大半が「X12+X13 を足すだけ」の課題に退化しており，深さ方向で踏んだのと同じ失敗を繰り返すことになる。

**XOR型**は，理論的な足場を失う。原論文の s(f)・r(f)・g(f) はいずれも mod 10 の加算構造を前提とした解析であり，XORにすると安全性パラメータが未定義になる。`func_13`・`func_22`・`func_31` との比較も成立しなくなる。また10進数のXORは自然に定義できず（4bit表現でXORして mod 10 とするなど，決め方に恣意性が入る），人間計算可能性も大きく損なう。さらに XOR は**演算の種類**を変えるものであって**動的参照の構造**を変えるものではないため，「動的アドレッシングが深層学習にとって困難か」という主題からもずれる。

## 4.2 「偶然より高い＝精度が出ている」とは限らない

前回，**「答え方がどうであれ，ランダム（10%）よりも正解率が高いなら，精度が出ていると捉えられるのでは」**とのご指摘をいただいた。この考え方は原則として正しいが，今回の関数族では**比較対象を一様ランダムのままにしてよいかが問題になる**ことが分かった。

足し算のない関数（k₂=0）では，答えは必ず鍵のどこかのマスの値になるため，正解の分布が鍵の数字ヒストグラムをそのまま反映する。したがって「その鍵の最頻値を答え続ける」だけの計算能力ゼロの戦略でも，16〜28%程度の正解率が出てしまう。

そこで比較対象を一様ランダム（10%）ではなく**鍵ごとの最頻値基準線**に置き換え，二項検定で有意に上回るかを調べた。

| 条件 | 正解率 | 最頻値基準線 | 基準線を有意に上回るか |
| :-: | :-: | :-: | :-: |
| 鍵A・深さ1 | 38% | 16% | 上回る（p<0.001） |
| 鍵A・深さ2 | 36% | 22% | 上回る（p=0.017） |
| 鍵B・深さ1 | 30% | 28% | 上回らない（p=0.429） |
| 鍵B・深さ2 | 26% | 26% | 上回らない（p=0.554） |

**同じ「30%前後」でも，鍵によって「意味のある精度」と「基準線と区別できない精度」が混在している。** 鍵Bの30%は，一様ランダム10%とだけ比べれば精度が出ているように見えるが，実質的には「何も学習できていない」場合と統計的に見分けがつかない。

なお，より厳しい基準（正解の分布を完全に知った上で独立に引く＝衝突確率 Σp²）と比較すると，全条件でこれを有意に上回っていた。したがって**モデルが何も学習していないわけではない**が，「偶然より高いから精度が出ている」と単純には言えない，というのが結論である。

## 4.4 鍵サイズ n の選択が偏りを左右する

鍵の値は常に0〜9なので，マス数 n が小さいほど出現する値の種類が減り，偏りが強くなる。

| n | 値の種類（平均） | 最頻値の占有率 | 衝突確率 |
| :-: | :-: | :-: | :-: |
| 10 | 6.5 | 28.0% | 19.2% |
| 26 | 9.3 | 20.8% | 13.6% |
| 50 | 9.9 | 17.7% | 11.8% |
| 100 | 10.0 | 15.1% | 10.9% |

n=10 では平均6.5種類しか現れず，偶然水準（10%）から最も遠い。**頭打ちを避けるために n=10 を選んだこと自体が，鍵の偏りという別の交絡を生んでいた**ことになる。足し算のある関数（次に実験する3つ）では緩和されるが，基準線の設定には引き続き注意が必要である。
