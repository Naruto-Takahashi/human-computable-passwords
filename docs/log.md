### 2026/07/17: 段階3（難易度ラダー × CNN同条件比較）完了 — 学習可能性の境界を特定

- **実施したこと**: 夜間バッチ（`scripts/run_stage3.sh`）で9本のQLoRA学習+held-out評価とCNNベースライン（全11アルゴリズム）を実行。共通条件: Bパラダイム（n_shot=0）・n_train=1000・エポック5固定・key_seed=0。全ログは `results/stage3_logs/`，比較図は `results/figures/stage3_boundary.png`。
- **結果（held-out 50件の正解率）**:

  | 条件 | LLM (3B QLoRA) | CNN |
  |---|---|---|
  | secret_add（鍵1桁） | 100% | 94% |
  | lookup_k4 / k10 / k26（純テーブル参照） | 100% / 100% / 100% | 100% / 100% / 100% |
  | table_add_k10（表10マス+mod和） | 100% | 88% |
  | **table_add_k26（表26マス+mod和）** | **8%** | **51%** |
  | **func_22（+ポインタ間接参照）** | **12%**（stage0/2とも） | 7% |
  | simple_add（鍵なし・生入力の加算） | **100%** | **10%** |

- **知見**:
  1. **記憶量は律速ではない**: 26マスの純テーブル参照（lookup_k26）は完全に学習できる。壊れるのは「テーブル参照値の算術合成」が加わり表が大きい場合で，**境界は L2 の k=10 と k=26 の間**。
  2. **func_22 の失敗はパイプラインのバグではなく本質的困難と確定**: 健全性確認済みのパイプラインで旧実験と同一の崩壊シグネチャ（loss≈0.192，token_acc≈0.925）が再現。ルール開示（stage2）でも改善しない（12%≈偶然水準）。
  3. **LLMとCNNは失敗の仕方が異なる**: simple_add はLLM 100% vs CNN 10%（事前学習された算術能力の恩恵），table_add_k26 は CNN 51% vs LLM 8%（CNNは部分的に近似）。「事前知識と合成できる規則はLLMが強く，生の関数近似はCNNが粘る」という対比。
  4. 留意: table_add_k10 は全100ペアが学習データに出現しうるためペア暗記と区別不能。k26の8%はペア暗記説も否定する（既出ペア77%なのに当たらない）。
- **次にやること**: (a) L2境界の精密化（k=13,16,20），(b) 失敗モデルへの `recover_key` 内省検査，(c) n_train=5000 での「データ不足か能力限界か」切り分け，(d) 複数鍵シードでの再現，(e) 週次報告への反映。

### 2026/07/17: 段階3（難易度ラダー + CNN同条件比較）完了 — 相転移境界を特定

- **実施したこと**: 難易度ラダー（L1 `lookup_k{4,10,26}`: 純テーブル参照 / L2 `table_add_k{10,26}`: テーブル2参照+mod和 / L3 `func_22`）を Stage 2（ルール開示）で，CNN同条件（Stage 0）を simple_add / func_22 / secret_add で，一括バッチ実行（各 n_train=1000, 5エポック, Bパラダイム, held-out 50件）。CNNベースライン（embed_cnn, 1000件）も全アルゴリズムで再取得。学習曲線は今回から自動保存（`training_curves.png` / `history.csv`）。
- **結果（held-out 正解率, 図: `results/figures/stage3_ladder.png`）**:

  | 条件 | QLoRA 3B | CNN |
  |---|---|---|
  | simple_add (stage0, 規則学習) | **100%** | 10% |
  | secret_add (stage0, 鍵1桁) | **100%** | 94.5% |
  | lookup k=4/10/26（記憶のみ） | **100/100/100%** | 100/100/100% |
  | table_add k=10（記憶+合成） | **100%** | 88% |
  | table_add k=26 | **8%（崩壊）** | 51% |
  | func_22（+ポインタ） | 12%（崩壊） | 7% |

- **知見**:
  1. **境界は「記憶量」ではない**: 26セルの純テーブル参照（lookup_k26）は両者とも100%。
  2. **LLMの崩壊点は「参照の合成 × クラス数」**: table_add は k=10（(X0,X1) 100通り）で100%だが k=26（676通り）で8%へ急落。学習済みペアに限っても8%であり，**暗記すら成立しなくなる**（k=10 では100ペアを完全暗記）。旧モード崩壊と同じ loss≈0.19 / token_acc≈0.925 シグネチャが再出現。露出回数の差（k10: 約50回/ペア vs k26: 約7.5回/ペア）が原因か，本質的限界かは n_train=5000 の追試で切り分け予定。
  3. **CNNは table_add_k26 で51%と部分的に汎化**しており，この段では CNN > LLM。一方 **simple_add では LLM 100% vs CNN 10%** と逆転（事前学習済みの算術回路の再利用と解釈できる）。学習器によって得意な構造が異なるという対比が得られた。
  4. func_22（ポインタ間接参照）は両者とも全滅（n_train=1000）。
- **次にやること**: (1) table_add_k26 / func_22 を n_train=5000 で追試（露出回数仮説の検証）,(2) 境界条件（table_add k=10〜26 の中間 k）を細分化，(3) 境界付近を3鍵シードで反復，(4) 週次報告へ反映。

### 2026/07/18: 段階3b（崖の細分化 + 露出回数仮説の検証）完了 — ポインタ間接参照だけが残る本質的困難と判明

- **実施したこと**: table_add k=13/16/20（n_train=1000）で崖の位置を細分化し，table_add_k26 と func_22 を n_train=5000 で追試（デタッチ実行のバッチ，全5本完走）。図: `results/figures/stage3b_cliff.png`。
- **結果（held-out 正解率）**: k=13: **100%** / k=16: **100%** / k=20: **24%** / **k=26@n=5000: 100%（復活）** / **func_22@n=5000: 12%（崩壊のまま）**。
- **知見**:
  1. **露出回数仮説が table_add については正しい**。崩壊は入力クラス数 k² とクラスあたり露出回数（≈ 5·n_train/k²）でほぼ説明でき，露出 約20回/クラスが成功の目安（k16@1000: ≈19.5回→100%，k20@1000: ≈12.5回→24%，k26@5000: ≈37回→100%）。つまり **テーブル合成はデータ量の問題であり本質的限界ではない**。
  2. ただし k=26@5000 は全676クラスが学習中にほぼ出現するため，「合成の獲得」ではなく**全クラスの暗記**で100%に達している可能性を排除できない。切り分けには「一部ペアを学習から意図的に除外して評価する」実験が必要（今後の課題）。
  3. **func_22 は n_train=5000 でも12%のまま**。ポインタ間接参照は入力クラス空間が大きく暗記が通用せず，データ5倍でも獲得されない。**難易度ラダーの中で唯一残った本質的困難はポインタ（動的な参照先の決定）**である。
- **次にやること**: (1) 週次報告（7/21）へ反映・提出準備，(2) 変更一式のコミット，(3) ペア除外実験（暗記 vs 合成の最終切り分け）の設計，(4) 8月から v2 in-context 相転移スイープへ。

### 2026/07/01: PoT学習方針の確定、Google Drive同期体制の確立、パースエラー問題の発見と対応

- **実施したこと**:
  - **Google Drive 同期体制の確立（rclone）**: 実験結果の長期保存先を OneDrive から Google Drive に移行。`rclone` を用いて `results/` フォルダを `gdrive:human-computable-passwords-results` に対し双方向同期する設定を確立。当初は `rclone mount` によるFUSEマウント方式を採用したが、ダッシュボードの読み込み速度（Loadingが長い問題）が生じたため、マウント方式を廃止しローカルフォルダのまま運用する方針に変更。実験終了後に `rclone sync` を自動実行するフック（`run_prompting.py` 内のバックグラウンドサブプロセス）を導入し、「実験完了ごとに自動同期」方式とした。
  - **パースエラー問題の発見（パースによる偽陰性の確認）**: `qwen2.5_0.5b_ft` の評価ログ（Stage 0 / `simple_add`）を確認したところ、モデルが JSON フォーマット（`{"answer": X}`）の代わりに日本語自然言語で「出力は X を出力します」「差分の値が XX なので〜」と回答してしまい、**パーサーが ERR（正解なしと判定）を返していた**ことを発見。これは「モデルが理解できていない」のではなく「モデルの出力フォーマットを現行パーサーが読み取れない」という**評価パイプライン側の問題（偽陰性）**であることを認識。
  - **PoT（Program-of-Thought）学習方針の確定**: パースエラー問題への根本的解決策として、学習ターゲット（Completion）を JSON から **Python コードブロック（`def predict_z(X): ...`）**に切り替える PoT 方式を採用することを決定。この方針は以下の理由で既存研究との比較上も妥当である：
    - 従来のML（CNN/Bi-LSTM等）が「重みの中で鍵とルールを同時に学習（暗記＋演算の一体化）」するのに対し、LLMは**「重みの中に鍵テーブルを暗記し、演算はPythonコードとして外部化（暗記と演算の分離）」**するという、LLM特有の役割分担の妥当性を測る新規の実験軸（RQ3）として位置づけられる。
    - パースエラーによるノイズを排除し、「モデルが生成したコードを実行した結果」により純粋な帰納・演繹能力の評価が可能になる。
  - **PoT 学習パイプラインの実装**: `train_finetuning.py` に `--use_code` フラグを追加。`generate_target_code()` ヘルパー関数により、各ジェネレータ（`simple_add`, `func_13`, `func_22`, `func_31`, `func_pow`）に対応した教師コードを自動生成する機能を実装。
  - **動作確認（PoT 評価パイプラインの疎通確認）**: `Qwen2.5-3B-Instruct` を `func_22 / stage0` に対し 10 件で PoT 学習（`--use_code`）を行い、その後 `--paradigm pot` で評価を実行。モデルが正しく `def predict_z(X): ...` のコードブロックを生成し、それが内部実行されて数値予測に変換されるパイプライン全体の疎通を確認した。
  - **CPU/メモリ最適化の適用**: `SFTConfig` に `dataloader_num_workers=4`, `dataloader_pin_memory=True` を追加し、データローダーのマルチコアCPU並列化とCPU→VRAM転送の高速化を実施。

- **得られた知見**:
  - **「パースエラーは評価の偽陰性である」という認識の確立**: モデルがJSON以外の形式で回答した場合に即座に ERR と判定するパーサーは、実際の正解率を過小評価する危険がある。PoT に移行することで、出力フォーマットがコードブロックに固定され、抽出・実行が機械的かつ確実になる。
  - **評価時の生成速度と学習品質の関係**: 未学習または学習不足のモデルは、指示に従えず Few-shot例題等を日本語で延々と繰り返し出力してしまう（バブリング）。これにより毎回の生成がトークン上限（512）まで走り評価が極端に遅くなる。十分に学習されたモデルは、コードブロックだけをピンポイントで出力して即 EOS を吐くため、評価速度が 10〜15 倍以上改善される見込み。
  - **Stage 0 × PoT の学術的意義**: Stage 0（プロンプトに鍵もルールも明示しない）でも、PoT 学習ではモデルが教師データ（Completion）として鍵とルールが書かれたコードを「見て」学習する。つまり、「プロンプト上は完全ブラインド」「重みの中に鍵を刷り込む」という構図になっており、これはケルクホフスの原理（アルゴリズム公開・鍵秘匿）のシナリオを最も正確にシミュレートしている。
  - **なぜ従来MLはアルゴリズムを学習できてLLMファインチューニングは難しいのか（理論的考察）**:
    - **勾配の到達範囲の違い**: CNN/Bi-LSTMは、損失（正解との誤差）の勾配が入力Xから出力Zまでの**全変換ステップ**に逆伝播する。一方、LLMのLoRAファインチューニングでは損失は「出力トークン列（例：`{"answer": 2}`）の予測誤差」にしかかからず、入力X（プロンプト側）への勾配はほとんど届かない。つまり「XからZへの変換方法」を学ぶ勾配信号がほぼ存在しない。
    - **LoRAの表現力制約（更新パラメータ量の問題）**: LoRAは全パラメータの約1%にしか更新をかけない低ランク近似更新である。鍵テーブル（26値）の記憶と演算回路（mod、間接参照）の両方を同時にこの小さなアダプター層に刻み込むには表現力が根本的に不足する可能性がある。CNNは全重みがこの1タスクに専念できる。
    - **ショートカット学習のリスク**: CNNにとっての正解ラベル「Z=2」は入力Xとの変換関係を学ぶ直接信号だが、LLMにとっての`{"answer": 2}`は「このプロンプト形式の後にこのトークンが来やすい」という表面的パターンとして学習されうる。アルゴリズムを理解した上で正解を導いているのか、統計的ショートカットを学んだのかが区別できない。
    - **PoT がこの問題を解消する理由**: 教師ターゲットを `def predict_z(X): sgm=[...]; ...` というコード列にすると、コードの全トークン（鍵の数値、演算子、インデックス）の予測に損失がかかる。これにより「鍵テーブルの各値の記憶」と「計算ロジックの構造」の両方に豊かな勾配信号が流れるため、LoRAアダプターへの情報量が大幅に増加する。

- **次にやること（Next Actions）**:
